# 一、架构书可行性与合理性审核

## 1.1 整体评价

这份文档在「已落地部分」（第一-四章 + 第七章前半）的描述**贴近代码现状**，注释也老实承认了"规划中/占位/降级"，质量在国内中型项目里属上乘。但它**身上挂着两套基因**：

1. **桌面端单机 + SQLite + LM Studio + Celery 本地降级** 的真实形态
2. **PostgreSQL + Kafka + Kong + Kubernetes + gRPC/Protobuf + ClickHouse + WebRTC + OAuth2.1+PKCE** 的"互联网中台"愿景

第二套基因**从未在代码中真正落地**，但仍然以"已落地"的口吻写在第六章（整体系统架构图）、第七章 7.5（安全）/7.6（监控）/7.10（消息队列）/7.12（数据库分层）/7.14（端到端时序）。这造成的最严重问题不是"文档不准"，而是**误导后续技术决策**——按当前文档招人/选型，会做出一堆给本地桌面端套互联网中台的过度设计。

## 1.3 能引起质的飞跃的改进点（不是修修补补）

我按"对当前产品形态收益最大"排序：

### 🚀 飞跃点 1：把 TTS 改成真流式，否则一切对话延迟优化都白搭

**问题**：当前链路是 `LLM_TOKEN 流出 → 等整句结束 → Kokoro 整句合成 → 分块发回`。LLM 流式输出的价值被 TTS 整句合成的 500-1200ms 完全吃掉。

**飞跃方案**：
- 短期：按句号/逗号切分 LLM 输出，**子句级流水线**（一句 LLM 完，立刻送 TTS，下一句并行生成）。Kokoro ONNX 是可以做子句合成的，首句延迟能从 1200ms 砍到 ~300ms
- 中期：评估 Kokoro 的 chunked decoding（按 phoneme 分块合成），做到真 token-aligned 流式
- 这一步做完，整个语音对话从"还行"跳到"竞品级体验"

### 🚀 飞跃点 2：把 analytics 从 SQLite 上拆出去，否则会成为下一个性能黑洞

**问题**：20 维度 × N 学生 × 每日全量计算 + 班级窗口聚合，全跑在 SQLite 单文件单写锁上。学生数 > 100 之后写锁阻塞主链路是迟早的事。文档 7.12 提了 OLAP 但代码里没动。

**飞跃方案**：
- 把 `StudentDailySummary` / `ClassDailySnapshot` / `AnalyticsArtifact` 独立成 **`analytics.db` 单独 SQLite 文件**（如果坚持单机），与主 `app.db` 物理隔离，至少避免写锁互相阻塞
- 桌面版本不要碰 ClickHouse；多机版本再上 DuckDB（嵌入式列存，零运维，原生 SQL 兼容好）
- 文档 7.12 整章应该重写为「桌面版：双 SQLite + DuckDB 物化视图」「云端版：PG + DuckDB」

### 🚀 飞跃点 3：建立"模型路由 + Prompt Registry + Context Store"的统一 orchestration 层

**问题**：文档 7.2.4 已经诚实承认"对话链与 analytics 链各搞各的 orchestration"。这意味着每个模块都重写一遍：超时 fallback、上下文压缩、Prompt 加载、metrics 上报。每加一个模块都是 O(N) 的实现成本。

**飞跃方案**：
- 抽出 `LLMInvocation` 单一入口：`invoke(scene, prompt_key, variables, context_id) -> stream | result`
- 内部统一处理：Prompt Registry 取版本 → Context Store 拼上下文 → ModelRouter 选模型 → 流式/超时 fallback → 写 PromptRegistry.metrics
- 改造完以后，新业务接入一个新场景只需要：写 Prompt 模板 + 写一个 scene 枚举。

### 🚀 飞跃点 4：作文/对话评分要做"评分一致性校验"，否则 LLM 评分是黑盒

**问题**：作文 6 维度评分、analytics 20 维度，**没有任何机制验证 LLM 评分稳定性**。同一篇作文连跑 3 次方差可能 > 10 分。教师端要把这种结果给老师看，会出大事。

**飞跃方案**：
- 对关键评分（作文 grade、analytics LLM 维度）实现 **n=3 多次采样取中位数 + 方差告警**
- 维护**金标准评分集**（教师人工评分 50 篇作文），每次 Prompt 版本升级跑回归测试，方差 > 阈值则拒绝发布
- 这是教育类产品和娱乐类 LLM 应用的本质区别——评分必须是可解释、可回归的

### 🚀 飞跃点 5：Barge-in 续接的"已播报/未播报"机制要做成对话主线，而不是局部补丁

**问题**：v1.9 加上的"已播报内容入历史 + 未播报内容标 interrupted"是亮点，但目前是 ad-hoc 实现，分别散落在 `main.py::abort_voice_request()` 和 `session.py::on_barge_in()` 两处。

**飞跃方案**：
- 把它升级为对话历史的**一等公民数据模型**：`Utterance { content, spoken_ratio, interrupted_at, interruption_reason }`
- 这一改造能延伸出：声纹断点续接、用户重听/重听位置标记、对话回放/教学回顾等高价值功能
